# Staging billing runbook (Stripe TEST mode only)

Live payments and production stay off. Nothing here uses a live key. Never paste
a key or signing secret into git, a chat, or an issue.

State when this was written: the Stripe **test** account holds one product
(`KEEL`) and nine prices; a webhook endpoint for
`https://keel-ai-staging.onrender.com/billing/webhook` is registered in Stripe;
**the Render services are not deployed** (that hostname answers
`x-render-routing: no-server`).

## 1. Deploy (Render dashboard) - once

Prerequisites from `STAGING_DEPLOYMENT.md`: a Neon database (run
`CREATE EXTENSION IF NOT EXISTS vector;` in it), Cloudflare R2 bucket + token,
a Groq key.

1. Render -> **New -> Blueprint** -> pick this repo, branch `KEEL_Test`. It reads
   `render.yaml` (services `keel-ai-staging`, `keel-frontend-staging`,
   `keel-redis-staging`; `keel-workers-staging` is a **paid** plan - skip it for
   billing tests).
2. When prompted for `sync: false` variables, set at least:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | Neon connection string |
   | `APP_DB_PASSWORD` | any new strong password (the migration creates the `ceopro_app` role with it) |
   | `MINIO_ENDPOINT`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` | R2 endpoint + access key + secret |
   | `CREDENTIAL_VAULT_MASTER_KEY` | a new key (see `backend/scripts/vault_key.py`) |
   | `STRIPE_SECRET_KEY` | the **test** key (`rk_test_...` / `sk_test_...`) |
   | `STRIPE_WEBHOOK_SECRET` | the signing secret shown for the staging webhook endpoint in Stripe |
   | `GROQ_API_KEY` | your Groq key |

   `JWT_SECRET` is generated by Render. Leave `UNASSIGNED_PLAN_ACCESS=none`.
3. Deploy. Build/start are in `backend/Dockerfile.ai` (`ENTRYPOINT
   docker-entrypoint.sh`): it applies all migrations, then starts uvicorn on
   `$PORT`. Health check path `/health`.
4. Check the real hostname Render assigned. If it is not
   `keel-ai-staging.onrender.com`, update the webhook URL in Stripe and
   `CORS_ALLOWED_ORIGINS` / `FRONTEND_BASE_URL` / `APP_BASE_URL` /
   `VITE_API_BASE_URL` to match.

Verify: `curl https://<backend>/health` -> `{"status":"ok"}`.

## 2. Link the Stripe catalog to the staging database - once, safe to repeat

From any machine with the staging `DATABASE_URL` and the **test** `STRIPE_SECRET_KEY`
in the environment:

```bash
cd backend
python -m scripts.stripe_sync_catalog --dry-run   # expect 9 x ADOPT, 0 x CREATE
python -m scripts.stripe_sync_catalog
```

The script reads the KEEL product and its active prices from Stripe and
reconciles with the database (see `src/ai/billing/catalog_sync.py`), so it
adopts what exists and creates only what is missing. It stops (exit 1) on any
mismatch instead of guessing. It does not rely on Stripe idempotency keys.

## 3. Webhook

The endpoint is `POST /billing/webhook`. In Stripe (test mode) -> Developers ->
Webhooks, open the endpoint, **Send test webhook**, pick any event. Expect HTTP
200 `{"received":true,...}`. 400 means the signing secret on Render does not
belong to this endpoint; 503 means `STRIPE_WEBHOOK_SECRET` is not set.

## 4. Hosted Checkout (test mode)

Sign in to the staging app as a company owner -> Billing -> choose Standard ->
Checkout. Pay with Stripe's published test card `4242 4242 4242 4242`, any future
expiry, any CVC. You are returned to `/billing?checkout=success`. The plan only
becomes active when the webhook arrives; the page does not trust the redirect.

## 5. Prices an operator must enter (nothing is guessed)

Every paid provider is refused until its real price is recorded:

```bash
python -m scripts.billing_admin set-price --budget ai --provider groq --operation <model> \
  --unit input_token --usd-per-million <price> --source "<where you read it>" \
  --verified-on <YYYY-MM-DD> --by "<you>" --reason "<why this price is right>"
```

(also `output_token`; see `docs/SUBSCRIPTIONS_AND_CREDITS.md` for the full list and
`set-control` for monthly caps / kill switches). Until then the AI assistant and
paid data sources answer 503 "pricing hasn't been set up" by design.
