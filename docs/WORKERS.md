# Workers and background tasks

All worker processes use the same checkout-local venv, restricted ceopro_app credentials and isolated Redis/DB as the API. Do not launch a second consumer accidentally. The root command records each child directly for ownership/readiness; it does not start a second competing supervisor. The existing `src.market_scraper.supervisor` remains available for deployments.

## Process inventory

| Name | Existing Python entry point | Work mechanism / dependencies | Startup evidence | Default |
|---|---|---|---|---|
| forecast | `src.ai.forecasting.consumer` | Redis `ceopro:stream:demand_forecast_requested`; PostgreSQL, MinIO, model pipeline; `AI_SERVICE_ACTOR_USER_ID` | Current PID's Redis consumer registration | core/full |
| images | `src.ai.marketing.image_worker` | PostgreSQL `image_generation_jobs`, storage and configured image provider | Current PID's `image_workers` heartbeat | core/full |
| connectors | `src.market_scraper.connector_worker` | Polls due sources; provider credentials are in existing credential vault | Native initialization log, shared DB validation, no startup exception | core/full |
| prices | `src.market_scraper.worker` | Receipt/legacy scrape streams, Scrapy and source policy | Native listening log and metrics endpoint | full |
| analysis | `src.market_scraper.analysis_worker` | Redis `market.analysis.requested`; existing analysis/DB | Current PID's consumer registration | full |
| discovery | `src.market_scraper.discovery_worker` | Redis `market.discovery.requested`; configured search/discovery providers | Current PID's consumer registration | full |
| enrichment | `src.market_scraper.enrichment_worker` | Redis enrichment queue, DB and provider evidence | Current PID's consumer registration | full |
| maintenance | `src.market_scraper.maintenance` | Periodic PostgreSQL recovery/maintenance; metrics | Successful native maintenance pass log | full |

Entrypoints above are run as `python -m <entrypoint>` from `backend/`. `DATABASE_URL`, `APP_DB_PASSWORD`, `SCRAPER_DATABASE_URL`, `REDIS_URL`, service actor IDs, storage and metric ports are generated by the launcher. Integration-specific credentials are optional; they do not prove working provider access.

The frontend/API process and workers are intentionally separate. A worker readiness check is initialization evidence, not proof that a real model or merchant job succeeded. Native job failures remain visible and follow the existing retry/accounting rules.

## In-process work

`src.ai.main._lifespan` starts:

- `market_discovery.refresh.start_background`: refresh scheduling.
- `notification_digest.start_background`: email digest polling.
- `billing.maintenance.start_background`: stale credit-reservation upkeep.

Their existing `*_ENABLED` and interval settings remain available. The launcher does not use `--lifespan off`.

Manual extraction uses `routers/extraction.py` and its existing background processing; there is no invented ingestion queue daemon. Knowledge document extraction/indexing uses the RAG pipeline. `src/infrastructure/messaging/ai_consumer.py` handles a separate legacy market-intelligence contract and is not an extra required unified runtime worker.

## Retries and failure behavior

Forecast, collection, analysis and discovery use native Redis consumer groups, claim idle pending work, record attempts and dead-letter after configured limits. Enrichment retains its queue deduplication/retry mechanism. Connector synchronization uses durable jobs/checkpoints and per-source diagnostics; failed runs must not advance checkpoints incorrectly.

Image workers claim PostgreSQL jobs, heartbeat, reclaim stale jobs and retry with bounded backoff. No fake AI image is introduced by the launcher. Maintenance recovers existing stale work according to approved policy; unresolved privacy/financial policies remain gated.

The developer launcher fails startup if an owned worker exits or its initialization/health evidence is missing. It does not silently restart a crash loop and call it healthy. Inspect logs, fix the cause and restart. Runtime task failures are visible in native job state, stream pending/dead queues and logs.

## Logs, status and individual debugging

`dev.ps1 logs --service discovery --follow` follows that worker. `status` checks recorded identities and available initialization evidence. Logs are private in `.dev/logs/`; never commit them.

For direct execution with the correct environment, use the Python environment-builder example in LOCAL_DEVELOPMENT and the entry point from the table. Stop the launcher-owned copy first. No worker receives migration-admin credentials.
