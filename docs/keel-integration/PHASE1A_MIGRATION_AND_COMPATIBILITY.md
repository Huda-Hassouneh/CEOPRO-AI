## Data and backfill behavior

- Existing permanent users, passwords, tenant memberships, subscriptions, trials, contracts and accounting receipts are retained. There is no Node account/hash import or automatic customer conversion.
- New signup stores only pending state before verification. Existing unverified customer accounts use the established account email verification/reset/login path; they are not deleted or migrated into pending records. Pending expiry uses the existing `EMAIL_VERIFICATION_CODE_EXPIRE_MINUTES`; retry cannot extend expiry or reset attempts. A live registration's password/code cannot be overwritten by another signup request. Lost browser nonce requires the original tab or waiting for expiry before a new registration; sessionStorage has same-tab memory fallback. No secret is put in URLs or persisted as an access session before verification.
- The numeric-code backfill marks older simultaneous PASSWORD_RESET/EMAIL_VERIFICATION rows used, preserving the latest per user/type and every historical row. Old superseded codes become invalid deliberately. Global hash uniqueness is replaced with account/type live-code uniqueness and independent invitation hash uniqueness, so different accounts may receive the same six digits safely.
- `users.credential_version` defaults to zero. Existing JWTs lacking `cv` map to zero and remain valid while unchanged; existing JWT claim names, lifetimes and max-session-age stay intact. Actual reset/password change increments the version, so all earlier sessions must sign in again; the settings UI clears the changed session accordingly. No blanket migration logout occurs.
- Tokens missing jti use a stable hash of the signed token for revocation. Durable hashed revocation receipts survive cache resets; positive Redis results deny, negative cache results require the DB receipt check. Unknown Redis or DB state returns 503. Confirm timeout/availability/SLO impact under native load before rollout.
- Customer suspension is distinct at company, global account and per-workspace membership levels. Per-membership suspension writes the existing removed_at as well as a separate suspension marker; restoration cannot revive an unrelated manual removal. Existing seat/accounting authority is reused. A platform administrator never receives exceptional financial authority through a tenant role, invitation role payload, customer ownership or support setting.
- Owner transfer atomically reassigns the platform authority and dedicated workspace role; the former owner retains admin only. Operator state is independent of all customer workspace roles. Tenant management endpoints reject management of the platform workspace.
- Financial approval receipts bind authenticated owner, reason, subject, explicit terms, expiry and request UUID. They are authorization records, not execution instructions. Existing pending quote/economic policies still govern any future activation. No below-floor amount, unpaid duration, FX rule, credit conversion or provider limit is invented here.

## CLI compatibility and operational boundaries

Existing mutating `scripts.billing_admin` commands now require `--by OWNER_USER_UUID --owner-token-stdin` and a valid current Python bearer token supplied through stdin. Require JWT_SECRET, healthy Redis, restricted auth DB connection and existing schema-owned billing connection. A bare user UUID/schema password is insufficient. Supply the token from an approved secret source without placing it in command arguments, shell history or logs. Existing accounting functions and historical approved_by text remain unchanged. Read-only `budgets` and trusted automatic `expire-reservations` retain their existing behavior; worker identities do not become customer privilege.

SMTP calls happen only after state commits. SMTP false/errors remain retryable and visible; failed delivery is never claimed as sent. There is no new email outbox; existing workers are preserved. Trial provisioning uses existing `billing.store.start_trial`, once per company/person; the existing logged failure/refusal leaves no active plan and is not bypassed by repeat verification.

## Recovery

Do not roll back to the old fail-open security implementation or delete verified accounts, memberships, financial approvals/audits, password versions or revocation receipts. Quiesce affected entrypoints if a native regression appears; preserve evidence, keep dependency failures closed, repair forward through the existing migration system and retest against the same source candidate. The full starting ZIP and pre-edit tracked/staged patches provide review/recovery material; they do not authorize destructive database rollback. Reconcile any failed trial or mail delivery using the existing billing/email authority without creating a second trial or bypassing explicit access policy.
