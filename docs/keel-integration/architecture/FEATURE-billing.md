# Feature architecture — billing

Status: PROPOSED for architecture review; capability families SUB PROMO CUSTOM PLATFORM. Single Python authority is already approved by user; no conflicting policy is selected.


Current Python UI: `PlansSubscriptionPage.jsx` → `billingApi.js` → `/billing/plans`, `/subscription`, `/trial`, `/checkout`, `/portal`, `/change-plan`, `/scheduled-change`, `/cancel`, `/resume`, `/invoices`, `/usage-history`. PlanChoice is `{plan_key,period_code}`; backend permits monthly/three-months/six-months/yearly, UI offers the first three. Subscription response retains camelCase fields (planId, billingPeriod, scheduledChange, canManageBilling, features, credits) and raw feature quantities. Billing role is owner/admin/accountant. Payment actions return 503 payments_not_configured; provider failures map to 502 provider_error.

`billing.service` uses existing customer IDs, current Stripe price mappings and Checkout idempotency. No activation on redirect. `/billing/webhook` verifies raw-body Stripe signature → webhooks.handle_event/_handle_locked → provider reconciliation and store writes. Keep Task 6 invoice/subscription/tenant identity locks, monotonic succeeded payments and event retry. `billing.store` owns assignments/customer/subscription/payment history. Never route a second webhook to a new independent state machine.

Node's mounted `modules/subscription/index.ts` imports singular `.route.ts` files. It adds plans/features/promo CRUD, `custom-plan.service` quote lifecycle and configurator/pricing policy, dedicated platform-admin screens, Node notification producers and effective-grant transition comparison. Do not copy the similarly named `.routes.ts` files simply because they look complete. Inspect app.ts's legacy cancellation import as an active dependency.

Promotion codes: Python create_checkout sets allow_promotion_codes=True, so it has Stripe-hosted entry but no equivalent managed Node promo tables/API/workflow. Node validatePromoCode checks active/start/end, plan association, global and per-tenant redemption counts; fixed-amount coupon currency comes from PROMO_FIXED_AMOUNT_CURRENCY. Node creates replacement Stripe coupons when discount terms change. Validation alone is not atomic redemption proof. Target one Python promo eligibility service plus provider-owned monetary discount, durable checkout reservation/confirmed redemption, unique provider/session binding, explicit stacking/abandon/expiry rules (PROMO-001). Preserve provider historical coupons rather than editing terms in place.

Custom plans: Node `calculateCustomPlanPrice` normalizes vendor units, estimated usage, competitor count/cadence (minutes per pricing month), infrastructure allocation and usage-driven rates; requires FX where currencies differ; computes total cost, total/(1-targetGrossMargin), optional vendor/maximumCostRevenueRatio, maximum floor, fixedPlatformFee, upward rounding increment. Snapshots carry rate IDs, feature configuration, FX source/time and override audit. `updateCustomPlanQuote` resets draft/calculation/approval. approve checks unsafe floor privilege/reason; send transitions with tenant notification; accept validates expiry, creates Stripe prices with frozen quote FX, and creates a tenant-private plan.

Python already has `billing.admin::set_custom_contract` which directly grants a separately approved operator contract and overrides, and cost_model plus verified provider_cost_schedules for runtime credits. Retain these; do not call direct activation on customer quote acceptance. New quote version tables link to the existing assignment/Stripe price owner; immutable accepted price/terms survive provider retries. Operator contract activation versus paid custom subscription is CUSTOM-001. Quote economics, FX, margins, fee thresholds and renewal rate snapshots require CUSTOM-002. No rates/FX from fixtures or invented plan values.

Target transaction: lock quote revision → verify permission/expiry/approval → record provider-action intent → Stripe call with deterministic idempotency outside long DB transaction → bind immutable price/session → signed billing webhook activates existing Python assignment → customer refreshes subscription state. Reconcile provider-success/DB-failure via durable intent; a checkout success page never activates rights. Sending an offer requires durable outbox plus idempotent consumer. Existing CLI remains supported and cannot silently override a newer Stripe subscription without an approved authority rule.

Plan changes compare effective Boolean grants, SUM allowances, MAX capacities, custom overrides and cadence rather than tier/price. Mixed gains/losses and already-over-capacity tenants need TRANSITION-001; retain schedules and pending payment outcomes. Catalog CATALOG-001 preserves Standard/Plus/Pro/Custom and old standard/pro keys/historical Stripe prices until new terms are approved. No public-price migration rewrites active customer rights.

Dashboards: retain Python patterns, translations, loading/error/empty and canManageBilling. Add promo entry/feedback; custom builder, safe offer/revisions; operator quote/rate/policy/catalog/companies/users screens under platform routes. Customer DTOs exclude costs/provider raw response. Every mutation has API authorization, audit, conflict state and persisted outcome; frontend checks are presentation only.
