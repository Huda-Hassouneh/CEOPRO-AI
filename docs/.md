# Test database writer account

This guide provisions a separate PostgreSQL login for a teammate who is
testing competitor, sentiment, evidence, RAG, source-policy, audit, and market
collection imports.

## Scope and safety

Use this only with a **separate test database**. Do not point this account at
production and do not give the teammate the backend, migration, owner, or
`ceopro_app` connection string.

The migration grants the `ceopro_ai_test_writer` login:

| Tables | Allowed operations |
|---|---|
| `global_competitors`, `tenant_competitors`, `competitor_product_mappings`, `competitor_prices`, `competitor_score_snapshots` | `SELECT`, `INSERT`, `UPDATE` |
| `reviews`, `sentiment_results`, `evidence_records` | `SELECT`, `INSERT`, `UPDATE` |
| `rag_documents_metadata`, `rag_document_chunks` | `SELECT`, `INSERT`, `UPDATE` |
| `data_sources`, `ingestion_jobs`, `import_staging_rows`, `market_observation_staging`, `market_observations`, `market_events` | `SELECT`, `INSERT`, `UPDATE` |
| `audit_logs` | `INSERT` only |

The login cannot delete rows, truncate tables, create or alter schema objects,
create roles or databases, replicate data, or bypass row-level security. These
are table-level grants; normal foreign keys, checks, and RLS policies still
apply. The account may need existing tenant, source, product, competitor, and
mapping rows to satisfy foreign keys before inserting dependent records.

**RLS limitation for this test account:** current tenant policies use the
PostgreSQL setting `app.current_tenant_id`. A direct database login can set
that custom setting itself. Therefore, this role can work with any tenant data
present in the test database by selecting that tenant ID. Keep only disposable
test data in that database. The grant is not a per-tenant security boundary.

## 1. Create the login in the test database

Create the role using your database provider's role-management UI, if it has
one. Otherwise, connect to the **test database** as its database owner and run:

```sql
CREATE ROLE ceopro_ai_test_writer
  LOGIN
  NOINHERIT
  NOSUPERUSER
  NOCREATEDB
  NOCREATEROLE
  NOREPLICATION
  NOBYPASSRLS;
```

Then set the password interactively in `psql` so it is not stored in a script
or shell history:

```text
\password ceopro_ai_test_writer
```

If the provider does not let you create database roles, ask its administrator
to create this restricted login. Do not work around that restriction by
promoting the application or migration account.

## 2. Apply the migration

Make sure the backend migration connection points to the **test database**.
Then run from the backend folder:

```powershell
npx prisma migrate deploy --config prisma7.config.ts
```

The migration checks that the role exists and has no elevated privileges. It
stops with a clear error if the role is missing or privileged. It does not
create or set the password.

## 3. Give the teammate the connection string

Use the test database host, database name, and this role's password. For a
standard PostgreSQL URL:

```text
postgresql://ceopro_ai_test_writer:<URL-encoded-password>@<test-host>:5432/<test-database>?sslmode=require
```

Use the SSL mode required by your provider. Send the URL through a password
manager or another private secret-sharing channel, never commit it to Git, and
never paste it into source code or a chat room. Rotate the password or drop the
login when testing ends.

## 4. Set the tenant context for each test transaction

For RLS-protected tables, set both context settings inside the same transaction
as the reads/writes. Replace the UUIDs with a test user and tenant in the test
DB:

```sql
BEGIN;
SELECT set_config('app.current_user_id', '<test-user-uuid>', true);
SELECT set_config('app.current_tenant_id', '<test-tenant-uuid>', true);

-- Run the test import statements here.

COMMIT;
```

The third `set_config` argument is `true`, so the settings are transaction-local
and reset at commit/rollback. With Prisma, set both values and do all related
writes inside one interactive transaction. Use `ROLLBACK` instead of `COMMIT`
for a dry run.

The current RLS helper checks that `app.current_user_id` is nonempty, then uses
`app.current_tenant_id`; it does not authenticate that user ID for a direct DB
login. The teammate can choose these settings. Treat them only as test query
context, never as a per-tenant access restriction.

## 5. What the teammate should confirm before importing

Ask them to provide the exact table/column mapping, whether each operation is
insert or upsert, and a small sample payload. The categories alone do not
define the required foreign-key IDs or write order. In particular:

- `data_sources` must exist before jobs that reference `source_id`.
- `ingestion_jobs` must exist before staging/observation rows that reference
  `job_id`.
- Competitor mappings must reference the correct tenant, product, and
  competitor rows.
- `sentiment_results` must reference an existing review.
- RAG chunks must reference an existing document and use the configured
  embedding dimensions/model version.
- Audit rows are append-only for this account.

Have them test with a few rows first, then verify the data in the test app.
