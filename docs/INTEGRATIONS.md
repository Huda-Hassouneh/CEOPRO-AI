# Local integrations

A healthy local runtime does not imply that external providers are configured. Setup creates no merchant connections, financial cost schedules, Stripe objects or customer subscriptions.

## Shopify and WooCommerce

Reuse the tenant connection screens, `src.market_scraper.provider_store_sync`, source lifecycle/vault and connector worker. Shopify OAuth/webhook configuration uses the actual Python onboarding endpoints; WooCommerce uses the tenant's store URL and approved API credentials.

Use authorized sandbox/test stores. Connection verification must succeed before Connected is shown. Initial/incremental sync stages provider records; manual review and approved canonical services manage promotion. Inventory requires explicit owner source/field/location mappings. Conditional automatic catalog promotion is disabled by default and retains its disposable-test restriction. Automatic invoice posting remains policy-blocked.

Shopify privacy intake authenticates exact-body signatures and shop/topic/source binding. Targeted irreversible privacy erasure/retention decisions remain tracked separately; local startup does not certify them.

Controlled fixture/worker/database evidence exists in the integration acceptance reports. **Real Shopify/WooCommerce merchant E2E is not certified by this developer setup.** Do not copy live merchant credentials into development.

### Shopify test-store setup

KEEL implements the standalone authorization-code flow. Consult Shopify's
[standalone app authentication](https://shopify.dev/docs/apps/build/authentication-authorization/authenticate-standalone-apps)
and [scope configuration](https://shopify.dev/docs/apps/build/authentication-authorization/manage-access-scopes)
references for the provider-side app setup; the paths below describe KEEL's code.

1. Use an authorized Shopify development/test store and an app you can install
   on it. Obtain that app's client ID and secret; place `SHOPIFY_CLIENT_ID`,
   `SHOPIFY_CLIENT_SECRET` and `SHOPIFY_REDIRECT_URI` in private
   `.dev/integrations.env`. No store access token belongs in a shared template.
2. The callback must be a public **HTTPS** API address ending
   `/onboarding/shopify/callback`, exactly registered in the app settings.
   Local loopback HTTP is rejected for this callback. If using a tunnel, route
   its API origin to the printed local API port; do not expose DB/Redis/MinIO.
   `FRONTEND_BASE_URL` is separately generated by the launcher for the browser
   return; do not put it in integrations.env or reuse an old checkout's origin.
3. Authorize the implemented read scopes: `read_products`, `read_orders`,
   `read_inventory`, `read_locations`. The request is built in
   `backend/src/market_scraper/shopify_oauth.py`; it validates required scopes,
   tenant/user binding, expiring single-use state and callback signatures.
4. Restart the local runtime after configuring the app, then use
   `/connect-data` → Shopify with the store's `*.myshopify.com` address and
   explicit connection consent. The UI calls
   `POST /onboarding/connect/shopify/authorize`, receives the browser callback,
   then completes `POST /onboarding/connect/shopify/complete` with a short-lived
   ticket. Successful tokens are vaulted per source, not returned to the UI.
5. Confirm verified source identity, run sync through the source action, inspect
   the job/checkpoint and staged product/order records. The `connectors` worker
   polls due verified sources. Provider records are not automatically proof of
   canonical business posting; review mappings/provenance and supported promotion gates.

Webhook intake exists at `POST /onboarding/shopify/webhooks/{source_id}`.
It checks exact-body HMAC, shop/topic identity, source ownership and delivery
replay before recording delivery. Register an actual HTTPS delivery URL for the
verified source when testing it; OAuth completion alone does not prove automatic
webhook registration. Supported topics are enumerated in
`backend/src/market_scraper/shopify.py`. Privacy intake does not certify completed
erasure/retention actions. Live install, callbacks and webhook delivery were not
performed during documentation verification.

Common failures: an unset redirect URI returns configuration-unavailable even
with client credentials; an HTTP/mismatched redirect, missing scopes or expired
state must be corrected through the app/authorization flow, not direct SQL.

### WooCommerce test-store setup

Provider-side [REST API key instructions](https://woocommerce.com/document/woocommerce-rest-api/)
cover key creation and non-Plain permalinks. KEEL's connection path is read-only
provider ingestion; use the least privilege needed for that test store.

1. Use a test WordPress/WooCommerce store on a public HTTPS origin with REST API
   v3 available under `/wp-json/wc/v3`. Use non-default compatible permalinks and
   verify that the API is reachable through the store's normal HTTPS routing.
2. In WooCommerce's REST API settings, generate credentials for an authorized
   test-store user with **Read** permission for verification/sync. KEEL's adapter
   reads products/orders; broader write permission is not required for that path.
3. In `/connect-data` → WooCommerce, supply the store URL, consumer key/secret,
   sync frequency and consent. `POST /onboarding/connect/woocommerce` validates
   `ck_...` / `cs_...` shape, performs authenticated provider verification and
   vaults credentials per source. Do not add shared WooCommerce keys to a global
   environment file, or put credentials/query secrets into the store URL.
4. Check verified source state, request sync and inspect the connector job,
   checkpoint, staged records and inventory provenance. Repeated sync should
   reuse provider identities, not duplicate sales. Canonical import/posting still
   requires its reviewed supported action; automatic invoice posting is gated.

The current customer connection flow uses polling; no automatic WooCommerce
webhook registration is promised. Signature utilities are not evidence of an
accepted end-to-end webhook lifecycle. Local/private addresses, unsafe redirects,
embedded credentials, custom ports and invalid API responses are rejected by
network/URL validation. For 401/403 check store key permissions; for 404 check
the store URL, REST routing and permalinks. Live-store acceptance remains open.

## Stripe TEST MODE (optional)

For optional, isolated lifecycle simulation see the [local Stripe Test Clock guide](STRIPE_TEST_CLOCK_LOCAL_GUIDE.md). Disabled by default; not part of production deployment.

The existing Python billing authority owns Products/Prices, promotions, quotes, Checkout, signed webhook reconciliation, entitlements and Credits.

Configure only an authorized `sk_test_` / `rk_test_` key and the real `whsec_` signing secret from your listener in private `.dev/integrations.env`. Restart after changes. The launcher refuses LIVE keys and incomplete signing configuration.

The actual webhook endpoint is `POST /billing/webhook`. In a separate terminal, use your installed Stripe CLI and an explicit event selection, for example:

```text
stripe listen --events checkout.session.completed,customer.subscription.created,customer.subscription.updated,customer.subscription.deleted,invoice.paid,invoice.payment_failed --forward-to http://127.0.0.1:<printed-api-port>/billing/webhook
```

Authenticate against your authorized TEST account first; inspect local `stripe listen --help` for the installed CLI version. Copy its listener-specific signing secret only into private configuration. Do not fabricate signatures, paste secrets in issues or start real payments as a setup smoke test.

Local migrations create feature/plan/provider-cost catalogs, not Stripe Products
or Prices. Publishing plan prices is the explicit operator
`python -m scripts.stripe_sync_catalog --dry-run` / sync workflow from `backend/`,
with authorized TEST configuration; inspect its adoption/drift plan first.
Do not run it as a routine health check. Checkout creation and redirect return
do not establish paid rights: signed, associated and idempotently reconciled
events must prove payment. Draft and zero-dollar trial invoices do not prove a
paid post-trial period. Plan changes retain approved trial/credit boundaries;
see [billing rules](SUBSCRIPTIONS_AND_CREDITS.md) and the
[billing operator reference](STAGING_BILLING_RUNBOOK.md).

For failed delivery, inspect the CLI delivery status and API webhook error,
the active signing secret and exact raw-body handling. For missing rights,
inspect associated event/payment state rather than granting entitlements by SQL.
Keep Test Clocks disabled unless performing the explicit local-only procedure.

Prior Stripe acceptance is historical evidence; no Stripe E2E is rerun by `dev.ps1 test`.

## AI and market providers

For the default assistant/text model, copy the optional integration template
only after setup, set `GROQ_API_KEY` from your authorized provider account and
retain `GROQ_MODEL=openai/gpt-oss-20b`, then restart. That model's approved rates
are installed automatically by startup migrations (USD 0.075/million input,
USD 0.30/million output); existing owner-configured rates remain unchanged.
No Platform Owner login is required to reapprove installed defaults. Other
models/providers need their own approved schedules; startup never fetches and
silently updates prices from provider websites.

Test credentials and model availability separately from paid inference. A valid
key does not prove quota, rate limits, cost configuration, tenant access or
credit settlement. Missing costs produce `COST_NOT_CONFIGURED`; exhausted rights,
provider caps or provider 429s have separate causes. Inspect redacted API/ledger
evidence; do not repeatedly regenerate to diagnose a setup failure.
Successful paid calls reserve estimated spend, settle measured token costs and
record provider USD separately from customer AI Credits. Cache-read fallback,
failure/finality rules and idempotency remain in the existing accounting code.

Knowledge documents use `/rag/documents/upload`; questions use `/rag/query`.
Optional semantic embeddings and reranking require model libraries/weights;
keyword fallback and the configured embedding backend are distinct from Groq
generation. Text grounding, citation/history and all-history sales scope need
their own tests. Marketing copy also uses factual grounding review, and image
jobs require their configured provider/storage path; a running image worker or
free-image fallback is not verified product-photography fidelity.

- `setup --models` installs the existing CPU/model libraries. Model weights may download from their actual hosts on first use. The launcher never substitutes dummy predictions.
- Hosted LLM/image/search credentials belong in `.dev/integrations.env`. Read `backend/KEYS_AND_ACCOUNTS_NEEDED.md` and `docs/SUBSCRIPTIONS_AND_CREDITS.md`.
- Configured credentials alone do not authorize spending. Verified cost schedules, entitlements, Credits and reservation/settlement rules still apply. See [RAG provider pricing and 503 diagnosis](RAG_ASSISTANT_503_FIX.md) for the separate credential and verified-cost requirements.
- Startup migrations install the [approved AI provider pricing catalog](DATABASE.md#approved-ai-provider-pricing-catalog), initially Groq `openai/gpt-oss-20b`, while preserving configured rates. No Platform Owner login or provider call is needed for bootstrap. Other models still need their own approved costs.
- Without confirmed financial inputs, pricing/paid operations remain unavailable with their existing messages. No fabricated rates/margins are inserted.
- SearXNG, local LLM/image servers and telemetry exist in the legacy Compose topology but are optional. They are not started as hidden prerequisites by the new local command.
- Browser-assisted scraping needs `python -m playwright install chromium` in the developer venv and may need OS dependencies. It is unnecessary for ordinary startup.
- OCR requires the Tesseract binary/language packs on PATH; without it the existing code reports unsupported/skipped OCR rather than invented extraction.

## Storage and email

Local MinIO uses the existing `src/infrastructure/Dockerfile.minio`, persistent per-checkout volume, generated credentials and loopback console/API ports. It is built from the repository's pinned source recipe; first startup needs registry/Go-module network access. Object buckets/prefixes are managed by existing application code.

Mailpit is a dedicated local SMTP capture and inbox, included by default so OTP/signup works without sending mail externally. Messages may contain synthetic PII and codes; keep the inbox local. No real SMTP account is configured or overwritten.

Production email uses the SMTP client in
`backend/src/ai/core/notifications.py`: configure `SMTP_HOST`, `SMTP_PORT`,
`SMTP_USE_TLS`, the sender and, where required, `SMTP_USERNAME`/`SMTP_PASSWORD`
through the deployment's secret settings. No particular hosted email vendor is
required or certified by this guide. The native launcher manages SMTP settings
for Mailpit, so do not override them in integrations.env. Warnings about missing
SMTP username/password are expected with unauthenticated local Mailpit; verify
actual message delivery before attributing them to a failure.

## Optional service boundaries

External AI, merchant stores, Stripe CLI, model weights, OCR binaries, scraper browser binaries, SearXNG, telemetry and local inference servers are separate prerequisites for their respective features. Their absence is a feature limitation, not a reason to misreport the entire local API as unhealthy. Conversely, a missing required DB/Redis/storage/mail/selected worker makes startup fail.

## Optional local image inference server

The actual entry point is uvicorn image_server.server:app from backend/ (default example port 7860). It has its own backend/image_server/requirements.txt and needs an explicitly supplied KEEL_IMAGE_MODEL_DIR with legitimate model weights. LOCAL_IMAGE_BASE_URL(S) connects the existing image provider to it. Its /health reports model/device/busy state. This is a separate heavy inference provider, not an implicit core dependency: it is not started without weights/configuration, and no image inference is claimed by worker readiness.
